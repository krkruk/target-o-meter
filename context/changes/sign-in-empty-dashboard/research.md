## Research Question

> We need to understand how to structure the application frontend for the first time, as this is the very first front-end related task.
>
> **Scope (revised 2026-07-25 — tightened to true S-01):**
>
> **A. Unauthenticated welcome page** — modern-app look:

> - A **Login** entry top-right (typical modern web app pattern).
> - A hero with marketing/welcome text (generated by the agent, concise and on-brand for ISSF sport shooters).

> - A **collapsible left-side menu** with:

## Summary

This is the **first frontend code in the repo**. The roadmap baseline states it plainly — *"Frontend: absent — no templates, no JS, no UI framework"* (`context/foundation/roadmap.md:53`). `src/frontend/` is an **empty directory**, there is **no `package.json`, no Vite config, no React, no Redux, no Oval, no CSS framework, no JS/TS files of any kind anywhere**. `django-vite>=3.1.0` is declared in the `dev` dependency group but is **not imported or configured anywhere**. There are **no SVGs** and **no `static/`/`public/` dirs** in the repo (40 real paper-target JPGs exist at `resources/paper_targets/` for CV fixtures, but those are gitignored training data, not user-facing assets — see §9).

The backend, however, is **already SPA-ready**. F-01 (`oauth-roles-scaffold`, archived done 2026-07-25) shipped:
- A working Auth0 OIDC + PKCE login flow (`/bff/login` → `/bff/callback` → `/bff/logout`) that sets a Django session cookie.
- A custom zero-email `identity.User` model keyed by OIDC `sub`, with the Owner role **derived** from `OWNER_SUB_ID` (never persisted), and a `nick` column (CI-unique, auto-filled with `shooter-<uuid8>` on creation).
- `GET /api/me` returning `{authenticated, user:{nick, role}}` (401 when unauthed) — **the ready-made seam the SPA uses to decide welcome-page vs. app-shell and to read the nick**.
- CSRF cookie pre-hardened for an SPA (`CSRF_COOKIE_HTTPONLY = False`), session cookie `SameSite=Lax` (load-bearing for the OIDC redirect), WhiteNoise wired.

The S-01 slice (this change) is **explicitly where React lands** — recorded as a deferred F-01 commitment in three places. F-01's templates (`templates/welcome.html`, `main.html`) are server-rendered placeholders explicitly waiting to be swapped for the React SPA, with **zero endpoint churn** (the URL contract `/`, `/bff/login`, `/bff/callback`, `/api/me` stays identical).

**Net answer for the user:** the frontend must be built **from absolute zero** — pick & install React + Vite + a state layer + styling, wire `django-vite` into `settings.py` + `templates/base.html`, mount the SPA at `/`, and ship **two screens** (welcome / app shell) plus the **username-on-first-login UX** (new `set_nick` service + `PATCH /api/me`). The welcome page uses a generated ISSF-target **SVG** stored as a static asset. Strong in-house precedent supports the skeleton/mock-first approach (F-02's `MockDetector`, F-01's empty `GET /api/users` returning `200 []`).

**Scope discipline:** the user's *original* brief described a full dashboard (hero stats, add-photo wizard with caliber/distance/camera, results list with correction dropdowns, month chart). **That content is deferred to S-02 (`photo-detection-review`) and S-03 (`accept-persist-dashboard`)** per the roadmap. S-01 ships the **shell**: the welcome page, the authenticated layout (collapsible left menu with Home + Logout-at-bottom, top bar with title + nick), and the nick-on-first-login flow. The main area inside the authenticated shell is a placeholder ("your dashboard will appear here" or similar) — the actual dashboard content lands in later slices.

**Full route table (only 5 routes exist today):**

| Path | Method | Handler | File:line | Auth |

**NinjaAPI object:** `api = NinjaAPI(title="Target-o-meter BFF")` at `src/bff/api.py:40`. `session_auth = SessionAuth()` at `:42`. django-ninja auto-enables CSRF for SessionAuth-protected state-changing routes; GET reads need no token.

**Login flow (`src/bff/routers/auth_routes.py`):**
1. `login_view` (`:59-68`) — validates `?next=` via `_safe_next` (open-redirect prevention at `:40-56`), stashes `next` in `request.session["oauth_next"]`, redirects to Auth0 `/authorize`.
2. `callback` (`:71-100`) — Authlib `authorize_access_token` auto-validates signature/iss/aud/nonce/exp → `userinfo`. Pulls `sub` (`:81-85`, 400 if missing). Calls `get_or_create_user_by_sub(sub)` (`:87`). Re-fetches ORM row, sets `user.backend = "django.contrib.auth.backends.ModelBackend"` (`:96` — required because `login()` is called without `authenticate()`), calls Django's `login(request, user)` (`:97`) which writes the `sessionid` cookie. Pops `oauth_next`, redirects to it (`:99-100`), default `"/"`.
3. `logout` (`:103-117`) — `request.session.clear()`, then redirects to Auth0 `/v2/logout`. **GET-based in F-01; S-01 should re-implement as POST + CSRF** (recorded F-01 plan-review F5 commitment).

**`GET /api/me` — the SPA's primary data source** (`src/bff/routers/session_routes.py:28-37`):
```python
@router.get("/me", auth=session_auth, response={200: MeOut})
def me(request) -> MeOut:
    try:
        dto = get_user_context(str(request.user.sub))
    except get_user_model().DoesNotExist:
        raise HttpError(401, "Session user no longer exists") from None
    return MeOut(authenticated=True, user=UserOut(nick=dto.nick, role=dto.role))
```
This serves "am I logged in?" (401 vs 200) and "what's my username?" (`nick` in the 200 body). GET needs no CSRF. **The dashboard consumes this.**

**No `set_nick` / `update_user` / `set_username` endpoint or service exists** (grep across `src/` confirmed). S-01 must add:
1. A `set_nick`/`update_user` service in `src/domains/identity/services.py` (none exists) returning a DTO, honoring the `identity_user_nick_ci_unique` constraint.
2. A mutation endpoint (e.g. `PATCH /api/me`) in `src/bff/routers/session_routes.py` guarded by `session_auth` + CSRF (django-ninja auto-enables CSRF for non-GET on SessionAuth routes).

### 4. Identity domain — what's already there for the username-on-first-login UX

- **`identity.User` model** (`src/domains/identity/models.py:87-147`): `AbstractBaseUser` + `PermissionsMixin`. Fields: `id` (UUID PK), `sub` (unique), `nick` (`CharField(max_length=64)`, CI-unique via `UniqueConstraint(Lower("nick"))` at `:118-126`), `is_staff`. `USERNAME_FIELD = "sub"` (`:110`).
- **Role is derived, not persisted** — `role` property (`:131-142`) returns `Role.OWNER` iff `self.sub == os.environ.get("OWNER_SUB_ID", "")`, else `Role.USER`. Fails closed on empty env.
- **`_generated_nick()` (`:24-30`):** `f"shooter-{uuid.uuid4().hex[:8]}"` — the F-01 fallback nick. **Every new OAuth user currently gets a `shooter-<uuid8>` nick on creation** via `UserManager.create_user` (`:59-60`) and `get_or_create_user_by_sub` (`services.py:34-37`).
- **No `has_set_nick` / nullable flag exists.** The model has only `id`, `sub`, `nick`, `password`, `last_login`, `is_superuser`, `is_staff`, `groups`, `user_permissions`. So S-01 has **three options** to distinguish "first login" from "has set nick":
  1. **Add a `has_set_nick` flag** (new migration) — cleanest signal, requires a schema change.
  2. **Treat `shooter-*` generated nicks as the "unset" sentinel** — no migration, but fragile (what if a user genuinely wants the nick `shooter-…`?).
  3. **Store the generated nick empty** (change `UserManager` to allow empty `nick` on creation) and gate on emptiness — but today the manager forces `_generated_nick()`, so this needs a manager change plus making `nick` nullable (migration).
  - **Recommendation for the planner:** option 1 (explicit `has_set_nick` BooleanField) is the most robust and least magic; it costs one trivial migration and one service branch. This is an open decision for `/10x-plan`.
- **DTOs (`src/domains/identity/dtos.py`):** `UserContextDTO` (`:18-31`, internal seam, **carries `sub`** — never client-facing), `UserOut` (`:33-37`, client-facing, fields `nick` + `role`, **no `sub`** — Zero Email Storage), `MeOut` (`:40-49`, `authenticated: bool`, `user: UserOut | None`).
- **Services (`src/domains/identity/services.py`):** `get_or_create_user_by_sub(sub)` (`:27-38`), `get_user_context(sub)` (`:41-49`, raises `User.DoesNotExist` → BFF maps to 401), `is_owner(dto)` (`:52-56`), `list_users()` (`:59-65`, empty until S-04). **No `set_nick`/`update_user`.**

### 5. Session / auth / cookie wiring (already SPA-ready)

- **Session is set in the OAuth callback** via Django's `login(request, user)` at `src/bff/routers/auth_routes.py:96-97`. The browser carries only `sessionid`; tokens stay server-side.
- **`request.session['sub']` is NOT used in the live code.** The AGENTS.md §6.2 example shows `user_dto = get_user_context(request.session['sub'])`, but the actual code reads `request.user.sub` (the ORM object populated by `AuthenticationMiddleware`):
  - `src/bff/routers/session_routes.py:31` — `get_user_context(str(request.user.sub))`
  - `src/bff/api.py:59` — same, inside `require_owner`
  - The session stores Django's standard `_auth_user_id`; `request.user` is resolved from that.
- **`@auth` / dependency pattern:** `session_auth = SessionAuth()` at `bff/api.py:42`. Applied per-route via `auth=session_auth`. `require_owner(request)` (`bff/api.py:45-64`) is an **authorization helper called inside the route body** (not in the `auth` list) — re-fetches the user, maps `User.DoesNotExist → HttpError(401)`, raises `HttpError(403)` if not Owner.
- **Cookie settings (`src/target_o_meter/settings.py:138-154`):**
  - `SESSION_COOKIE_HTTPONLY = True` (`:138`)
  - `SESSION_COOKIE_SECURE = SECURE_COOKIES` (False dev / True prod, `:141`)
  - `SESSION_COOKIE_SAMESITE = "Lax"` (`:146`) — **load-bearing** for the OIDC callback (Strict would suppress `sessionid` on the cross-site redirect → Authlib finds no nonce → silent failure).
  - `SESSION_COOKIE_AGE = 60*60*8` (`:148`)
  - **`CSRF_COOKIE_HTTPONLY = False` (`:154`)** — explicitly *"HttpOnly=False on the CSRF cookie: a future SPA (S-01) must read `csrftoken` to send it on POSTs."* SPA-ready.
- **Middleware (`settings.py:89-103`):** SecurityMiddleware, **WhiteNoiseMiddleware** (`:91`, correct position right after Security), SessionMiddleware (`:92`), CommonMiddleware, CsrfViewMiddleware (`:94`), AuthenticationMiddleware (`:95`), `DevAuthBypassMiddleware` (`src/target_o_meter/dev_auth_bypass.py`, self-gates on `DEBUG=False`), MessageMiddleware, XFrameOptionsMiddleware.
- **Production guards** (`src/target_o_meter/checks.py:18-57`): `E001` hard-refuses boot if `DEV_AUTH_BYPASS_SUB` set + `DEBUG=False`; `W001` soft-warns if `OWNER_SUB_ID` empty in prod.

### 9. Welcome-page assets — the ISSF-target SVG and the static-file story

The user asked for a **generated SVG** of a paper target, stored as a file in the application. Findings that shape how this lands:

- **No SVGs exist anywhere in the repo** (confirmed by repo-wide `find`). The only images are 40 real paper-target JPGs at `resources/paper_targets/*.jpg` — these are **CV training fixtures** (gitignored as training data per `resources/` conventions), **not** user-facing assets, and must not be used on the welcome page (privacy: they're real shooters' targets).
- **No `static/` or `public/` directory exists yet.** Django's `STATIC_URL = 'static/'` and `STATIC_ROOT = BASE_DIR / "staticfiles"` are set (`settings.py:238-239`), but `STATICFILES_DIRS` is **unset** and there is no app-level `static/` dir.
- **Three viable homes for the SVG** (the planner picks):
  1. **Vite-handled (`src/frontend/assets/target.svg`)** — imported into React, hashed by Vite, bundled into `dist/`. Cleanest for an SPA: the SVG becomes a build asset, served via WhiteNoise in prod. Works for both an `<img src={targetUrl}>` and an inlined `import TargetSvg from './assets/target.svg?react'` (SVGR-style).
  2. **Django static (`src/frontend/static/target.svg` or a dedicated app `static/`)** — served by Django/WhiteNoise at `/static/target.svg`, referenced by absolute URL. Bypasses the Vite pipeline; simpler but loses hashing/HMR.
  3. **Inline in the component** (`<svg>...</svg>` JSX) — zero asset plumbing, full CSS control, but bloats the component and can't be cached separately.
  - **Recommendation:** option 1 (Vite asset) — it matches the SPA-first posture, gets hashing + caching, and keeps the SVG under `src/frontend/` where the rest of the frontend lives. Option 3 (inline) is a fine fallback for a small, simple target graphic.
- **What the SVG should depict.** An ISSF pistol target is a series of concentric scoring rings (10 at center, descending to 1 outermost) on a cream/off-white card, conventionally with a black inner bull (rings 7–10) and a small inner "X" ring at the center. A faithful-but-simple vector rendering (concentric circles + ring numbers + the black inner zone) is appropriate for a welcome illustration — it reads instantly as "a shooting target" without needing a photoreal asset. Dimensions: a 10m Air Pistol target is 170×170 mm; a 25m/50m Precision target is 550×550 mm — the SVG `viewBox` should be square and scale via CSS.
- **Sourcing/licensing.** An original SVG hand-authored (or generated) for this project avoids any third-party-license question. Do **not** scrape an ISSF target image — the real target designs are official, and reusing a photograph of a real target raises both licensing and the privacy concern noted above. An abstract concentric-ring target is generic and safe.

### 10. How auth is exercised across environments (clarification)

> Added in response to: *"How are we going to test it in DEV? Mock authenticator / user-password form? For real Auth0 — native Auth0 UI for the `sub`?"*

**Key invariant:** the `sub` is the *only* identity anchor. Auth0's entire job is to prove "this browser owns `sub` X." Everything else (nick, role) lives in our DB. So "stubbing Auth0" just means "produce a `sub` without doing the Auth0 round-trip." There are **three modes**, none of which is a user/password form we build:

**Mode 1 — Dev bypass (day-to-day local dev).** Already shipped by F-01 (`src/target_o_meter/dev_auth_bypass.py`). **No form, no Auth0, no password.** A Django middleware registered immediately after `AuthenticationMiddleware` auto-authenticates every request as the `sub` named in `DEV_AUTH_BYPASS_SUB` when `DEBUG=True`. It is **stateless** — never calls `login()`, never touches the session; it sets `request.user` directly, and `SessionAuth` trusts `request.user.is_authenticated`. On first hit it `get_or_create`s the `identity.User` row with nick `dev-<sub[:8]>`.

- To use: set `DEV_AUTH_BYPASS_SUB="auth0|dev-bypass"` in `.env`, run the dev server, hit `/` — `GET /api/me` returns `200` as that user. (Documented in `.env.example:26-29` and `src/domains/identity/README.md:34`.)
- **Role impersonation:** set `DEV_AUTH_BYPASS_SUB` **equal to** `OWNER_SUB_ID` to be the Owner; set them different to be a plain User. Flip roles by editing `.env` + restart. (The role reads `OWNER_SUB_ID` from env at request time, so tests flip it per-test via `monkeypatch.setenv` — see `src/domains/identity/test_utils.py`'s `make_owner`, which deliberately does *not* touch the env.)
- **Prod safety — two independent guards (both load-bearing):**
  1. `target_o_meter.E001` (`src/target_o_meter/checks.py:32-37`) — a Django system check at boot: if `DEV_AUTH_BYPASS_SUB` is set while `DEBUG=False`, `manage.py check` exits non-zero and the app **refuses to start**. Runs at runserver/gunicorn/Render-deploy boot.
  2. The middleware itself (`dev_auth_bypass.py:69`) — `if not settings.DEBUG: return None`. Belt-and-suspenders because E001 runs at boot, not in gunicorn's serving loop on Render. Two failures would have to align for the bypass to be live in prod.

**Mode 2 — Real Auth0 (the native Auth0 hosted UI).** This is the answer to *"for real Auth0, native UI?"* — **yes, we use Auth0's hosted login page; we do not build a credential form.** That is the point of OAuth / the BFF pattern. Already wired by F-01 (`src/bff/routers/auth_routes.py`):

1. User clicks **Login** → SPA does a full-page nav to `/bff/login` (`auth_routes.py:59`).
2. `login_view` redirects to Auth0 `/authorize` with PKCE (`code_challenge_method=S256`), scope `openid profile` — **no `email`**, so Zero Email Storage is enforced at the scope level, not just by dropping a column (`bff/oauth.py:22-24`).
3. **Auth0 shows its own UI** (login form, social buttons, MFA, sign-up, password reset) on `*.auth0.com`. We never see the password, never render a credential field.
4. Auth0 redirects back to `/bff/callback` (`auth_routes.py:71`); Authlib's `authorize_access_token(request)` does the server-side code exchange and auto-validates signature/iss/aud/nonce/exp.
5. We extract **`sub`** from `userinfo` (`auth_routes.py:81-85`, 400 if missing) — that's all we take.
6. `get_or_create_user_by_sub(sub)` find-or-creates the `identity.User` row; Django `login()` sets the session cookie; redirect to `/`.

- To use locally: set `AUTH0_CLIENT_ID` / `AUTH0_CLIENT_SECRET` / `AUTH0_DOMAIN` in `.env`, **leave `DEV_AUTH_BYPASS_SUB` unset**, then click through Auth0's hosted UI for real. Useful for a one-off sanity check; too much friction for day-to-day dev.

**Mode 3 — UAT/E2E against real Auth0 (Playwright).** Already scaffolded by F-01 at `tests/acceptance/conftest.py:24-48`: `uat_base_url` + `uat_auth0_creds` parametrizable across `"user"`/`"owner"`, **skip-on-missing-secret** so CI never fails for lack of creds. The actual UAT test was deferred by F-01 and never landed; S-01 doesn't add auth logic, so it doesn't need a UAT test either. This is the pattern for when a slice genuinely must validate the real Auth0 round-trip.

**Which mode does S-01's testing use?**

| Context | Mode | Mechanism |
|---|---|---|
| **Backend/system tests** (pytest + Django test client) | **Neither bypass nor Auth0** | `client.force_login(user, backend="django.contrib.auth.backends.ModelBackend")` via the `_login_as` helper at `tests/system/test_auth_flow.py:24-27`. Bypasses *both* Auth0 and the dev middleware — sets the session as if login succeeded. **This is the pattern S-01's new `set_nick` / `PATCH /api/me` tests will use.** |
| **Local manual dev** (you, in the browser) | **Mode 1** (or Mode 2 for a sanity check) | Set `DEV_AUTH_BYPASS_SUB` → logged in. Unset it + set `AUTH0_*` → real Auth0 hosted UI. |
| **CI** | pytest suite via `force_login`; UAT job is shell-only | `.github/workflows/uat.yml` gated on `vars.UAT_ENABLED == 'true'`, no-op until a UAT test exists. |

**Implication for S-01 scope:** S-01 adds **no new auth code**. The SPA consumes `GET /api/me` to decide welcome-page vs. app-shell; login is a full-page nav to `/bff/login` (already works); the only new backend touch is the username-on-first-login service + `PATCH /api/me` (FR-002). The dev-bypass already makes local SPA development trivial — set `DEV_AUTH_BYPASS_SUB` and you land in the app shell immediately, which is exactly what's needed to develop and visually verify the welcome page, the collapsible menu, the top-bar nick, and the nick-on-first-login prompt.

## Architecture Insights

1. **Zero endpoint churn is the contract.** F-01 was designed so the URL surface (`/`, `/bff/login`, `/bff/callback`, `/bff/logout`, `/api/me`) stays identical when S-01 swaps templates for React. The SPA mounts at `/` (served by `bff/views.py:index`), login is still a full-page redirect to `/bff/login`, and `/api/me` is the bootstrap call. The only new endpoint S-01 adds is the username mutation (`PATCH /api/me` or similar).
2. **BFF pattern, server-held sessions.** The browser holds only `sessionid` (HttpOnly, SameSite=Lax). Tokens never reach the client. The SPA identifies the user via `GET /api/me`, not by decoding a JWT. CSRF: read `csrftoken` cookie, send `X-CSRFToken` header on mutations (django-ninja enforces it for SessionAuth non-GET).
3. **Domain isolation is hard-enforced.** `.importlinter contract:1` (domains independent) and `contract:2` (BFF above domains) are CI gates. S-01's new username flow must be: router in `src/bff/routers/` → service in `src/domains/identity/services.py` → ORM in `src/domains/identity/models.py`. No shortcuts.
4. **Owner role is environmental, not persisted.** `OWNER_SUB_ID` is read from env at property-call time. The SPA learns the role from `/api/me`'s `role` field; it does not infer it. This affects what menu items the app shell shows (e.g. an "Admin" entry visible only when `role === "owner"` — parked for S-04 but the SPA can already conditionally render it).
5. **Skeleton-first is the established pattern.** Both F-01 and F-02 shipped stubs/shells before real integration (F-02 `MockDetector`, F-01 empty `GET /api/users`). S-01 shipping a welcome page + app shell with a dashboard **placeholder** (no real content) is consistent and expected — the dashboard content lands in S-02/S-03.
6. **`SameSite=Lax` is load-bearing for OAuth.** Do not "tighten" the session cookie to `Strict` — it would break the Auth0 callback (the cross-site redirect would arrive without `sessionid`, Authlib would find no nonce, and login would silently fail). The cookie settings are correct as-is.
7. **`GET /api/me` is the auth seam for the SPA.** A single bootstrap call decides which screen to render: 200 → app shell (read `nick`, `role`), 401 → welcome page. This keeps all auth state server-side (no client-side JWT, no client-side auth flag to get out of sync) and is the only endpoint the SPA needs to load the shell.
